# Дивергенции форка от апстрима — реестр защиты

`docs/UPSTREAM.md` — это очередь **на отправку** (временная дивергенция: появилась в форке,
исчезнет, когда автор влил PR). Этот файл — про другое: то, что **останется отличным от апстрима
навсегда**, по нашему собственному решению, даже после того как соответствующий PR будет влит.
Риск, который он закрывает: при слиянии/синхронизации с `upstream/main` человек (или агент) видит
«о, это же уже есть у автора» и молча берёт версию автора, стирая осознанное отличие форка.

## Правило

У каждой permanent-дивергенции — **три привязанные друг к другу вещи**:

1. **Маркер в коде** — комментарий `// FORK: <id> — <короткая причина>. docs/FORK_DIVERGENCE.md#<id>`
   рядом с диверг. строкой/функцией. Маркер — не для человека, а для `git grep`: он либо есть в дереве,
   либо пропал. Пропал без записи в этом файле про retire — сигнал «слияние что-то съело».
2. **Строка в таблице ниже** — тот же `<id>`, что искать (`grep`-паттерн), почему это навсегда,
   каким тестом доказано, что поведение не откатилось молча.
3. **Тест**, который ломается, если дивергенция исчезнет из бинаря (не только из текста diff'а —
   поведение). Текстовый маркер может выжить, а функция за ним — откатиться; тест ловит именно это.

`scripts/check_fork_divergence.py` сверяет (1) и (2) автоматически — гоняется вручную перед
релизом форка и **обязательно после любого слияния `upstream/main`** (см. процедуру внизу).
Свести (3) в автоматику может не каждая дивергенция (сборочные гейты, например) — там достаточно
(1)+(2) и ручной проверки по процедуре синхронизации.

## Реестр

| id | где | почему навсегда | апстрим сейчас | доказано тестом |
|---|---|---|---|---|
| `base64-default-heuristic` | `src/utils.h/.cpp` `Base64Hint::Auto` + `resolveBase64Input()`, вызовы в `avro_methods.cpp:1520,1791` | У автора (после [#88](https://github.com/NuclearAPK/Simple-Kafka_Adapter/pull/88)) `IsBase64` — обычный `bool = false`, без эвристики: не так исторически вызывали 1С-код, который никогда не передавал этот параметр. В форке `Auto` (аналог «параметр не передан», `Неопределено` со стороны 1С) обязан сохранять СТАРУЮ эвристику `tryBase64Decode` — иначе у всех существующих вызовов в конфигурации молча меняется поведение задним числом. Это разница в default'е, а не в наличии фичи — она не исчезнет, даже когда #88 будет влит | #88 открыт; после влития у автора всё равно останется plain `bool=false`, у нас — tri-state с эвристикой по умолчанию | `scripts/avro_selftest/base64_hint_test.cpp` (6/6: покрывает `ForceYes`/`ForceNo`/`Auto` на бинаре и на чистом base64) |

Строк пока одна — ниже критерий, когда реестр вырастет достаточно, чтобы задуматься о переименовании
компоненты (см. «Когда переименовывать»).

## Процедура синхронизации с апстримом (защита от потери)

```bash
git fetch upstream
# 1. Снимок «что у нас fork-only» ДО слияния — по каждой topic-ветке дивергенции
git log --oneline main ^upstream/main > /tmp/fork-only-before.txt

# 2. Слияние (не rebase — история слияний уже используется в этом форке,
#    смешивать стратегии на середине истории только даст лишние конфликты)
git merge upstream/main

# 3. Маркеры дивергенции пережили слияние?
python3 scripts/check_fork_divergence.py   # exit != 0 -> STOP, разбираться, а не коммитить

# 4. Поведение пережило слияние, не только текст?
#    (полный набор self-test'ов форка — расширять по мере роста реестра)
cmake --build build/selftest --config Release
ctest --test-dir build/selftest

# 5. Патчи не «испарились» логически — сверить патч-ID форк-only коммитов до/после
#    (ловит случай, когда слияние тихо взяло чужую версию того же куска кода)
git range-diff <upstream-до-синка>...main <upstream-после-синка>...main

# 6. Обновить "апстрим сейчас" в таблице реестра, если у автора появилось похожее —
#    решить явно: остаёмся разными (запишем почему) или дивергенция закрыта (retire строку,
#    убрать маркер из кода — одним коммитом, не как побочный эффект слияния).
```

Шаг 3 — обязательный gate, не «если будет время». Шаги 4–5 — минимум перед релизом форка
(`X.Y.Z-fork.N`), не обязательно после каждого мелкого fetch.

## Когда переименовывать компоненту

Не переименовываем по факту количества строк в реестре — переименовываем, когда дивергенция
перестаёт быть «то же самое + одна явная поправка» и становится «другое поведение по умолчанию,
о котором пользователь типовой компоненты не подозревает». Конкретные триггеры (любой один):

- Реестр permanent-дивергенций вырос до **3+** независимых пунктов (сегодня — 1).
- Появилась дивергенция, меняющая **сигнатуру** существующего метода (не просто новый опциональный
  параметр) — тогда это не drop-in замена бинаря автора, и молчать об этом в имени — нечестно.
- Дивергенция меняет поведение **без флага** (т.е. нельзя получить поведение автора, просто не
  передавая новый параметр) — уже само по себе повод хотя бы явно писать «form fork».

Пока не сработал ни один триггер — имя `SimpleKafka1C` / `Simple-Kafka_Adapter` (fork) остаётся;
дальнейшее решение о ребрендинге — за Славой, когда сработает.

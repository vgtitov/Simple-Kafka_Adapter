# Постмортем: ошибка декодирования AVRO и доработки компоненты

**Период:** июнь 2026. **Версия с фиксами:** `1.9.1-fork.2`.
**Симптом в 1С:** `Ошибка AVRO-декодирования: Error decoding AVRO: vector::_M_range_check: __n (which is 18446744073709551583) >= this->size() (which is 2)` на сообщениях крупного топика (~170 КБ на сообщение, Confluent Wire Format, рекурсивная схема).

---

## 1. Итог (TL;DR)

Корень проблемы — **НЕ схема, НЕ версия avro-cpp и НЕ байты сообщения**, а **граница 1С → нативная компонента**: платформа 1С при передаче `ДвоичныеДанные` в метод нативной компоненты маршалит тело **как base64-строку** (без паддинга; возможны переносы строк; приходит и строкой, и blob'ом). Компонента трактовала это как сырые байты Avro, срезала 5 «байт» Confluent-заголовка (а это символы `AAAAA…`, не настоящий заголовок) и десинхронизировала бинарный декодер → индекс ветки union читался как мусор (`-33`) → `vector::_M_range_check size=2`.

**Фикс:** на входе декода компонента распознаёт валидный base64 и раскодирует его (`tryBase64Decode`). Магия Confluent `0x00` / OCF `Obj\x01` не является символом base64, поэтому сырой бинарь с base64 не путается.

---

## 2. Хронология и что было исключено

`18446744073709551583 = 2^64 − 33` → индекс **−33** в вектор размера **2**. Размер 2 = число веток union `["null", T]` (или enum `stateName` из 2 символов). Отрицательный индекс ветки = **рассинхрон декодера**.

Последовательно проверено и **исключено**:

1. **Версия avro-cpp.** Гипотеза: баг рекурсивных схем в avro-cpp < 1.12.1. Пересобрали на **1.12.1**, добавили метод `ВерсияСборки`/`GetBuildInfo` → подтвердили, что в проде реально работает 1.12.1. **Ошибка осталась.** (1.12.1 всё равно нужен — на старых версиях рекурсивная схема падала отдельно.)
2. **Схема.** Дамп `НастройкиAVRO.СхемаJSON` из 1С побайтно совпала со схемой из реестра (md5). Schema id у всех сообщений верный. **Схема ни при чём.**
3. **Байты.** Файлы `.bin`, сохранённые из 1С (`ДвоичныеДанные.Записать`), декодились автономным `avro_selftest` на 1.12.1 — **14/14 OK**. Значит сами байты чистые.
4. **Метод/код декода.** Декод идёт через `ДекодироватьСообщениеAVRO` (`compileJsonSchema` → срез Confluent-заголовка → `binaryDecoder` → `GenericReader`) — стандартный и корректный.

Парадокс «всё совпадает, а не работает» снялся диагностикой: в текст ошибки компоненты добавили **отпечаток принятого** (`[recv: тип size first16]`). В журнале:

```
[recv: STRING size=222459 first16=41 41 41 41 41 77 53 63 ...]
```
- `222459 = 166844 × 4/3` (без паддинга) — коэффициент расширения base64;
- `41 41 41 41 41 77 53 63` = ASCII `AAAAAwSc` = `Base64("00 00 00 03 04 9C …")` = base64 от реального Confluent-заголовка.

→ В компоненту приходил **base64-текст тела**, а не байты.

---

## 3. Первопричина

1С при вызове нативного метода с параметром `ДвоичныеДанные` передаёт тело **как base64**. Наблюдалось:
- тип на стороне C++: и `STRING` (VTYPE_PWSTR), и `BLOB`;
- без `=`-паддинга; в общем случае возможны переносы строк и URL-safe алфавит.

`decodeAvroMessage`/`getAvroSchema` принимали это за сырые байты → срез 5 символов base64 вместо заголовка → рассинхрон бинарного Avro → `vector::_M_range_check`.

---

## 4. Решение

**`src/utils.cpp` — `tryBase64Decode`:** устойчивый декодер base64:
- оба алфавита (`+/` и URL-safe `-_`), padded и unpadded, пропуск пробелов/переносов;
- возвращает `false` на любом не-base64 байте → вызывающий берёт данные как есть.
- Безопасность: Confluent-сообщение начинается с `0x00`, OCF — с `Obj\x01`; эти байты не входят в алфавит base64, поэтому сырой бинарь никогда не распознаётся как base64 ошибочно.

**`src/avro_methods.cpp` — `decodeAvroMessage` / `getAvroSchema`:** вход (и STRING, и BLOB) материализуется и, если это валидный base64, раскодируется в локальный буфер; иначе берётся как есть. В текст ошибки добавлен отпечаток `[recv: …]`.

**Проверено** на точном входе сервера (unpadded base64 `222459` → `166844` → декод OK), на всех 14 repro-сообщениях (14/14), и на вариантах с переносами строк / URL-safe.

### Сопутствующие фиксы
- **`putAvroSchema`** теперь **перезаписывает** схему по имени (был «register-once» — обновление молча игнорировалось; в переиспользуемом экземпляре могла застрять устаревшая схема).
- **`GetBuildInfo`/`ВерсияСборки`** — версия компоненты + версии слинкованных библиотек (avro-cpp, librdkafka, boost, protobuf, fmt, curl, zlib, openssl). Позволяет из 1С увидеть, какой бинарь реально загружен (метка в имени файла врала).

## 5. Сборка (обязательно для воспроизведения)

- **avro-cpp ≥ 1.12.1** — обязательно (на < 1.12.1 краш рекурсивной схемы; гейт в `scripts/Dockerfile.ubuntu20` и `scripts/build_windows.bat`).
- **fmt force-include**: avro `Exception.hh` зовёт `fmt::format`. На avro-cpp 1.12.1 + fmt 12.1 сборка проходит и без него (перепроверено 27.07: `Exception.hh` тянет `<fmt/core.h>`, а тот — `format.h`), но на других сочетаниях версий падает на `'format' is not a member of 'fmt'`. В `CMakeLists.txt` добавлен `-include fmt/format.h` (`/FI` на MSVC) как страховка.
- `scripts/triplets/x64-linux-static.cmake` — отсутствовавший overlay-триплет (без него Dockerfile падал на `COPY`).
- `.dockerignore` — контекст сборки без `.git`.
- `scripts/avro_selftest/` — standalone регресс-тест декода (схема + .bin / base64), повторяет путь компоненты.

## 6. Ревью компоненты (память / ресурсы / потокобезопасность)

Внесено в ветке оптимизаций:
- `getMessage()`/`consume()`: `RdKafka::Message*` → `unique_ptr` (утечка при исключении); `consume()` больше не пишет за границу буфера librdkafka (был `slice(payload,0,len)` с записью `\0` в `payload[len+1]`); тело без лишней копии (~200 КБ).
- Декод AVRO использует локальный буфер, не затирая член `messageData` (тело последнего kafka-сообщения).
- `setParameter()/setPartitioner()`: upsert настроек (нет накопления дублей и рассинхрона `clientID()`[первое] vs `getSettingValue()`[последнее]); проверка типов.
- `clRebalanceCb.offsets`: мьютекс (гонка/двойной delete с фоновым потоком poll librdkafka).
- `putProtoSchema`: overwrite; проверки типов параметров в `produce()`; подбор ветки union в `fillAvroFromJson` по типу JSON (для union с >2 ветками).

## 7. Заметки по Assign-режиму (1С)

- Промышленный контур переключён с Subscribe на Assign. Assign делает прямой `hConsumer->assign()` без членства в группе/rebalance.
- **Общая метка исключения потока** в модуле интеграции на стороне 1С ловит ЛЮБОЕ исключение и подменяет текст. Реальную причину смотреть в журнале регистрации и в регистре состояний потоков.
- Периодическая ошибка в Assign: на каждом цикле `ПолучитьСостояниеПартиций` → `GetConsumerLag` (метаданные + committed offsets, таймаут 5 с, новый admin-клиент). Периодически таймаутит → роняет цикл. Происходит **до чтения**, поэтому offset не сдвигается, потери данных нет — просто пропущенный цикл.
- **Offset-safety:** 1С коммитит только реально вычитанное и обработанное/персистированное (коммит только после успешной обработки). Непрочитанное/необработанное → не коммитится → перечитывается (at-least-once).
- Рекомендации: (1) пробрасывать реальную причину вместо generic-текста (сделано); (2) транзиентный таймаут `GetConsumerLag` не должен ронять весь поток (ретрай/мягкий пропуск); (3) не тянуть полное состояние партиций на каждом цикле — назначать один раз.

## 8. Как проверить, что загружен правильный бинарь

```bsl
Компонента = ...;
ЗаписьЖурналаРегистрации("KafkaDiag", УровеньЖурналаРегистрации.Информация,,, Компонента.ВерсияСборки());
// ожидаем: SimpleKafka1C version=<версия релиза>
```

При сбое декода текст ошибки теперь содержит отпечаток `[recv: тип inLen b64dec first16 size]` — сразу видно, что реально пришло в компоненту.
